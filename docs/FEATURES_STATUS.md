## Section 1 — Document Purpose & Scope

### 1.1 Role in Repository Documentation
`FEATURES_STATUS.md` serves as NEXORA's authoritative feature-level implementation tracking registry. While **Technical Blueprint v2.1** defines the system architecture, workflows, data domains, and engineering standards, `FEATURES_STATUS.md` decomposes every approved architectural area into discrete, trackable features with empirical implementation status, workspace ownership, existing code/endpoint/database evidence, testing verification, and unresolved design dependencies.

### 1.2 Architectural Scope Tracked
In accordance with **Technical Blueprint v2.1**, this registry tracks:
- **2 Primary Application Pages:** Page 1 (`Welcome to NEXORA — Select Your Workspace`) and Page 2 (`Unified Retail Management Dashboard`).
- **4 Stakeholder Workspaces (UI Context Only):** `Store Manager (Admin)`, `Inventory Staff`, `Purchase Manager`, and `Finance Staff` (with **zero** login, password, or JWT authorization workflows).
- **18 Core Modules** organized across **5 Operational Groups** (`M01`–`M18`).
- **4 Supporting System Capabilities** under **Group 6** (`SYS-01`–`SYS-04`), tracked separately and **never counted as additional core modules** (`22` registry areas in total across both categories).
- **8 Explicitly Excluded Capabilities** (`EXCL-01`–`EXCL-08`) retained outside project boundaries.

### 1.3 Feature ID Assignment & Maintenance Protocol
- **Versioned Active Identifier Scheme:** To guarantee zero collision with the legacy 13-module `v1.0` registry identifiers (`HEAD` commit `8dcbfd4`), every active Blueprint v2.1 feature uses a strictly versioned namespace:
  - **Core Module Features:** `FEAT-V2-M<NN>-<FF>` (e.g., `FEAT-V2-M01-01` through `FEAT-V2-M18-11`).
  - **Supporting Capability Features:** `FEAT-V2-SYS-<NN>-<FF>` (e.g., `FEAT-V2-SYS-01-01` through `FEAT-V2-SYS-04-14`).
- **Historical ID Non-Reuse Rule:** The `58` legacy `FEAT-M01-01` through `FEAT-M13-04` identifiers from `v1.0` are permanently retired from active feature assignment and preserved solely in **Section 1.4** for audit continuity. Legacy identifiers must never be reassigned to revised 18-module scopes (for instance, `v1.0` `M01` was *Role-Based Home Dashboard* whereas `v2.1` `M01` is *Product Management*).
- **Identifier Stability & Rename vs. Retirement Rules:**
  - Every `FEAT-V2-*` identifier is permanently bound to its functional requirement and must **not** be renumbered when implementation status changes or when new features are appended to a module.
  - **Editorial Clarifications / Scope Expansions:** Refining a feature's wording or expanding clarification details without changing its core responsibility preserves the same `FEAT-V2-*` ID.
  - **Removal or Fundamental Replacement:** If an active `FEAT-V2-*` feature is later dropped or replaced by an incompatible design, its original ID must be marked `RETIRED` rather than reusing the slot for an unrelated requirement.
- **Maintenance:** Whenever a task implements, modifies, or verifies a feature, the responsible developer/agent must update that feature's `Status`, `Relevant Files`, `Relevant Endpoints`, `DB Tables`, `Testing Status`, and `Notes / Limitations`, and recompute module and summary totals immediately.

## Section 2 — Feature Status Definitions & Evidence Rules

### 2.1 Allowed Status Vocabulary

| Status | Meaning |
| :--- | :--- |
| `IMPLEMENTED` | Core functionality exists in repository source code and is empirically verified against real execution/tests on the active branch. |
| `PARTIALLY IMPLEMENTED` | A meaningful functional subset exists in the repository (e.g., backend service/route code), but complete end-to-end execution, artifact readiness, database persistence, or UI integration remains incomplete. |
| `PLANNED` | Approved in Technical Blueprint v2.1 scope, with no implementation code or persistence layer present on branch `main`. |
| `POSTPONED` | Approved as a possible future enhancement beyond current academic scope, deliberately deferred. |
| `EXCLUDED` | Explicitly prohibited from project scope under NEXORA architectural boundaries (`EXCL-01`–`EXCL-08`). |

### 2.2 Verification & Classification Governance Rules
1. **File Presence Is Not Proof:** A file existing in `backend/` or `frontend/` does not prove that its target capability operates cleanly.
2. **Endpoint Presence Is Not Workflow Completion:** An API route stub or isolated inference route does not prove an entire retail workflow or database persistence exists.
3. **Passing Unit Tests Are Bounded:** Synthetic unit tests passing does not establish full UI, MySQL, or cross-module integration.
4. **Logical Entities Are Not Tables:** Blueprint logical database entities must never be reported as live MySQL tables without verified SQLAlchemy models and executed migrations.
5. **Placeholders Are Not UI Features:** `frontend/README.md` does not constitute an implemented React or Tailwind interface.
6. **Module Status Follows Feature Evidence:** A module is marked `IMPLEMENTED` only when all core feature requirements work end-to-end; it is `PARTIALLY IMPLEMENTED` when meaningful working code exists alongside unimplemented features; otherwise it is `PLANNED`.
7. **Live Evidence Over Prior Reports:** Every status in v2.2 was checked directly against branch `main` (`8dcbfd4`). On live `pytest backend/tests/ -v` inspection (`60` collected tests), **44 tests passed** (`41` ML/unit tests across `test_preprocessing.py` `5/5`, `test_feature_engineering.py` `7/7`, `test_ml_features.py` `10/10`, `test_model_training.py` `10/10`, `test_model_evaluation.py` `9/9`, plus `3` core app/API tests in `test_main.py`) while **16 setup errors** occurred in `test_forecast_api.py` (`TestForecastAPI.setUpClass` `FileNotFoundError`) because `.gitignore` excludes `backend/ml/models/*` (leaving `.gitkeep` until `python backend/ml/src/train.py` generates `.joblib` binaries and `models_metadata.json` locally). Those `16` setup errors are missing-artifact blockers rather than passing or failing assertions, and runtime API/serialization features affected by missing local binaries are documented transparently below.
